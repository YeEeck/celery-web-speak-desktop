# 启动条目由应用在运行时拥有，操作系统状态是唯一真相

随系统启动需要在操作系统侧登记一条启动条目：Windows 是当前用户 Run 键下的一条值，Linux 是 XDG autostart 目录下的一个 .desktop 文件。这条登记有两个候选写入方——安装器（`[Tasks]` 询问、`[Registry]` 写入并随卸载删除）与应用自身（运行时调用 Electron 登录项 API）；也有两种状态真相——config.json 记录"用户意愿"并在启动时对齐，或直接以操作系统的实际状态为准。

决定写入方只有一个：应用在运行时。安装器只承担卸载清理，创建条目不参与——便携 ZIP 没有安装器却要提供同一能力，若由安装器写入则两种分发形态行为分叉；两处同时写还会产生"最后写入者获胜"和重复条目。状态真相取操作系统：菜单勾选每次打开都重读系统条目，config.json 不新增字段。用户的意愿在系统里本来就可见——任务管理器禁用启动项不删除 Run 值，只写一条未公开的 StartupApproved blob，因此 Electron 的 `openAtLogin` 会继续返回 true，读取必须走 `launchItems` 的 enabled。让配置再存一份意愿等于允许三处状态互相漂移，还要写"启动时对齐"的逻辑，而现有配置写入在切换服务器时本就会重置偏好字段。

代价有二：卸载清理必须由安装器按**同一个值名**删除，否则用户卸载后每次登录都会撞上"找不到程序"的错误框；条目记录的路径在应用被移动后需要在下一次启动时自愈。

备选方案：安装器拥有（`[Tasks]` 询问、`[Registry]` 写 Run 值、`uninsdeletevalue` 清理）——便携版覆盖不到，且引入第二个写入方；config.json 存意愿——多一份可漂移的状态，并与现已存在的偏好重置缺陷叠加。
