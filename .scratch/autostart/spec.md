# autostart

随系统启动（Windows 独占）：让用户勾选一次后，登录到桌面会话即自动运行本应用，且登录拉起时不打扰。

方案决策见 [ADR-0004](../../docs/adr/0004-startup-entry-owned-by-application.md)，术语见 [CONTEXT.md](../../CONTEXT.md)「随系统启动」。

## Problem Statement

客户端目前只能手动启动。每次开机后用户都要自己在开始菜单或桌面找到图标点开，才能接上语音；对"先开语音再进游戏"或"会议前先登录语音"这类高频场景，这一步每天重复，且容易忘记——忘了就意味着队友找不到人。

操作系统的启动框架本来就支持按用户登记"登录后自动运行"，但本应用完全没有用到；更麻烦的是现有文档把"开机启动"写成了明确的非目标（README、架构文档、应用音频设计各一处），用户即使去找也找不到入口。

## Solution

在标题栏"更多"菜单里增加一个「随系统启动」勾选项（仅 Windows 正式包）。勾选后由应用在操作系统侧的当前用户启动条目中登记自己；取消勾选即删除登记。

勾选的显示永远来自操作系统的真实状态：用户在任务管理器的"启动"页禁用或删除条目后，菜单里会自动变成未勾选——应用不替用户"修复"，也不假装自己还在启动。

由启动条目拉起时，应用以最小化出现在任务栏、不抢焦点、不弹任何提示；服务器不可达时切出的配置页同样最小化。用户需要时点任务栏即可。

## User Stories

1. 作为每天开机就进语音的 Windows 用户，我希望勾一次「随系统启动」，so that 以后不用每天找图标才能进语音。
2. 作为不想被启动项拖慢机器的用户，我希望默认不勾选，so that 我不主动同意就没人替我在启动项里加东西。
3. 作为自己用任务管理器管理启动项的用户，我希望在任务管理器里禁用后被应用如实反映，so that 菜单勾选与系统行为不会各说各话。
4. 作为把便携版解压到 U 盘或另一个目录的用户，我希望移动目录后它仍然能在登录时启动，so that 换了位置不用重新勾选。
5. 作为卸载了应用的用户，我希望启动条目随之消失，so that 我不会在每次登录时遇到"找不到程序"的弹窗。
6. 作为登录后想先做别的事的用户，我希望应用不要抢走焦点，so that 我不用先处理一个凭空出现的窗口。
7. 作为登录后才发现服务器没启动的用户，我希望应用安静地待在任务栏，so that 我不会被一个突然弹出的配置页打断。
8. 作为想知道语音是否已经就绪的用户，我希望从任务栏恢复窗口就是正常界面，so that 最小化只是不打扰，不是功能缺失。
9. 作为使用 Linux 的用户，我希望不要看到一个点了没反应的开关，so that 我不会以为客户端坏了。
10. 作为开发者，我希望开发模式绝不登记启动条目，so that 我的机器上不会被塞进一个指向 electron.exe 的自启动项。
11. 作为想关掉这个行为的用户，我希望再次勾选同一项即可关闭，so that 关闭路径与开启路径一样明显。
12. 作为误触勾选的用户，我希望取消勾选立即生效、无需重启，so that 我能马上确认它已被关掉。
13. 作为把应用装到非默认目录的用户，我希望条目路径跟随实际安装位置，so that 换盘安装后依然能启动。
14. 作为同时装了安装版和便携版的用户，我希望两者共用一份配置却不会互相覆盖启动条目，so that 我运行哪个版本就登记哪个。
15. 作为关注隐私的用户，我希望这个开关只做操作系统登记、不上报任何信息，so that 它不成为新的数据出口。
16. 作为用键盘操作菜单的用户，我希望这个勾选项能像其它菜单项一样被方向键选中并触发，so that 键盘操作不被破坏。
17. 作为在配置页（切换服务器）状态下浏览菜单的用户，我希望也能看到这个开关，so that 我不用先进过服务器配置才能改它。
18. 作为排障的用户，我希望开关的写入失败能被记录到本地日志，so that 勾选没生效时我有迹可查。
19. 作为审阅文档的用户，我希望 README 与架构文档不再声称"不提供开机启动"，so that 文档与实际能力一致。
20. 作为只想要语音悬浮窗、不想任何自启动的用户，我希望这个开关是纯粹的可选能力，so that 它不影响浮层、更新检查等既有行为。
21. 作为在同一台机器上有多个 Windows 账户的用户，我希望只对我自己的账户生效，so that 我不替别人做决定。

## Implementation Decisions

- **新增一个主进程模块负责启动条目**，对外只暴露三件事：读取是否启用、设置启用与否、把漂移的路径改回当前可执行文件。操作系统细节（注册表、登录项 API、平台差异）全部收在模块内部。
- **模块通过一个可注入的后端访问操作系统**，后端接口形状如下（测试用伪实现，生产用 Electron 登录项 API）：

  ```ts
  interface StartupEntry {
    enabled: boolean
    path: string | null
    args: string[]
  }

  interface StartupEntryBackend {
    read(): StartupEntry
    write(path: string, args: string[]): void
    remove(): void
  }
  ```

  读取返回的是"操作系统承认的状态"，因此后端必须自己处理"条目存在但被外部禁用"与"条目存在但路径不是当前程序"这两种情况，而不是把原始注册表值直接抛给上层。
- **条目名固定为 `Celery Web Speak`**，不使用 Electron 默认的 AUMID 派生名（默认值形如 `electron.app.<ProductName>`），因为这个名字会直接显示在任务管理器的"启动"页。固定名字还有一个硬约束：卸载清理必须按同一个名字删除。
- **状态读取不使用 `openAtLogin` 或 `executableWillLaunchAtLogin`**：前者在 Windows 上忽略 StartupApproved，用户禁用后仍返回 true；后者只按 AUMID 命名的值判断，自定义名字下不可靠。改为读登录项列表，按"名字匹配 + 当前可执行文件路径"判定启用状态。
- **写入的参数是 `--autostart`**，由主进程在最早阶段解析命令行，决定窗口的呈现方式。
- **登录拉起时"显示后再最小化"**：先按记录恢复尺寸（包括最大化），再显示，再最小化。这样用户从任务栏恢复时看到的是他上次的窗口状态，而不是一个被降级成默认尺寸的窗口。
- **不新增 config.json 字段**，配置版本不升级，切换服务器时的既有重置逻辑不受影响。
- **菜单**：新增一个动作与一个勾选状态字段；菜单状态对象从"单个布尔"扩展为"按动作索引的勾选集合"。该菜单项在远程模式与配置模式下都显示（它是机器级属性）。弹出窗口的高度是常量，需要随项目数调整。
- **平台与构建门控**：仅 `win32` 且仅打包运行时显示该菜单项；开发模式与非 Windows 平台下动作被白名单拒绝，主进程侧不产生任何系统写入。
- **写入没有错误通道**：登录项 API 返回 void。因此每次切换后重新读取状态并以读取结果为准绘制勾选——开关"弹回去"就是失败信号，同时写一条本地日志（成功、失败、自愈各一个事件名）。不弹对话框、不伪造成功。
- **自愈时机**：应用初始化完成后、窗口创建前做一次路径核对；只有在条目存在且启用、且记录的路径与当前可执行文件不一致时才改写，其余情况一律不写，避免每次启动都动注册表。
- **安装器不创建条目**，只在卸载流程里按同一值名删除一次（值不存在时静默跳过）；卸载时"是否删除用户数据"的既有询问不变。
- **术语统一为「随系统启动」**，代码、日志事件名、UI 文案、文档都用这一个词。
- **不新增任何跨进程协议**：远程页面不感知这个开关，Web 端无需发版。

## Testing Decisions

好的测试只断言外部可见行为：菜单打开时显示的勾选与系统条目一致、登录拉起后窗口处于最小化、卸载后条目消失。不断言"调用了哪个 API"或"内部标志位取值"——这些是实现的自由。

三条接缝，按"能高不低"排列，且全部复用现有接缝，不新增测试基础设施：

1. **启动条目模块的公开接口（新增的唯一接缝）**：用伪后端替换操作系统，覆盖五种状态——条目不存在、存在且启用、存在但被外部禁用、存在但路径漂移、写入抛错。断言模块返回的启用状态与它在后端上造成的副作用（写了什么、删了什么、有没有无谓写入）。先例：更新检查器用伪 store 对象注入（同样的"依赖以最小接口注入"手法）。
2. **命令行解析的纯函数（已有单元测试风格）**：`--autostart` 的识别与其它参数的共存。先例：窗口状态、Origin 策略等一批纯函数单测。
3. **现有 e2e 启动接缝**：给现有 Electron 启动 helper 增加"追加参数"的能力，用 `--autostart` 启动后断言首个窗口 `isMinimized()` 为真、且无参数启动时行为不变；服务器不可达时配置页同样最小化。先例：现有 e2e 已经用 `isMaximized()` 断言过窗口状态、用 `getByRole('menuitem')` 断言过菜单项。这条接缝在 Linux 上可跑，因为"最小化呈现"被刻意做成与平台无关。

已知覆盖缺口，需要如实记录：CI 只在 Linux runner 上跑 e2e，Windows runner 只跑类型检查与单测，因此"勾选 → 注册表 → 任务管理器可见"这条真实链路没有自动化覆盖。补一个 `test.skip(process.platform !== 'win32')` 的端到端用例供 Windows 本地运行，并在测试决策里写明它在 CI 中恒被跳过，而不是伪装成已覆盖。

已落实：`tests/e2e/application.spec.ts` 的"真实 Windows 启动条目写入、读取与删除"用例在 Windows 本地验证"Electron 写入 → 注册表 → 生产读取"链路，其余平台与 CI 中恒被跳过；`src/main/startup-entry-registry.test.ts` 另在 Windows 上覆盖含空格路径、中文路径与 StartupApproved 禁用态。

实测还修正了一条实现决策：Electron 的 `launchItems` 只按传入路径过滤，且在可执行文件路径含空格时读不到自己写入的条目（本应用安装路径必然含空格），既无法回显勾选，也无法发现漂移条目。因此写入/删除继续走 Electron 登录项 API，读取改为直接读注册表（Run 值 + StartupApproved），见 ADR-0005。

## Out of Scope

- Linux（AppImage / unpacked）的 XDG autostart 支持——后续独立票据，路径漂移与无卸载器两个问题需要单独设计。
- 托盘常驻、隐藏启动、关闭到托盘：本应用关闭即退出，无托盘，隐藏启动不可见也不可救。
- 安装时询问"是否随系统启动"，以及安装器创建条目。
- 开机时机控制：延迟启动、错峰启动、仅在网络就绪后启动。
- 用户在任务管理器禁用后自动重新启用（我们只如实反映，不修复）。
- 远程 Web 设置面板里的同名开关（需要跨仓协议升级，且该偏好是机器级而非账号级）。
- 自动更新、后台消息推送、macOS。

## Further Notes

- Windows 的启动值是一条用户级注册表值，写它不需要管理员权限；值数据是命令行字符串，受 260 字符限制，因此只追加一个短参数。
- "被外部禁用"的状态由系统以未公开的二进制 blob 记录，Electron 只认得其中"禁用/启用"两种取值；这也是为什么状态必须从登录项列表读，而不能从"条目是否存在"推断。
- 便携版与安装版共用同一份用户数据目录与单实例锁，两者不能同时运行；启动条目登记的是"最后一次勾选时正在运行的那个可执行文件"，因此自愈规则是"跟随当前可执行文件"，而不是"记住安装路径"。
- 应用音频的既有约束不变：不装驱动、不装服务，本特性同样不引入任何后台常驻进程。
